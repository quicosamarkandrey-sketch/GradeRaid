Open **Sections → New Section**, enter the grade and section name, and attach the roster. Create the section, review the names, then choose **Create accounts**. For a section that already exists, use **Import roster** on its card.

Use an Excel `.xlsx` file or a UTF-8 `.csv` export. The importer reads the first sheet. It accepts a **Name** or **Full Name** column, **First Name** and **Last Name** columns, or one full name per row in column A without a header. Each import accepts up to 100 data rows and a 1 MB file. Invalid and duplicate rows in the file are flagged in the preview. Matching names already enrolled in the target section are skipped. Names alone cannot distinguish two students with the same name or reliably identify a student from a different section.

Download the starter-login CSV from the results and distribute each student's row privately. Students can enter their generated **student login** on the regular sign-in screen and change the starter password under Profile. The generated login stays fixed and points to an Auth address without a mailbox. Email reset and self-service username changes for these accounts require a verified recovery workflow. An authorized Supabase administrator can reset a lost password in Authentication → Users. Store or dispose of credential exports according to school policy. The app keeps starter passwords in memory for the current dialog. A lost or interrupted export cannot be regenerated from the roster; keep the dialog open when retrying unconfirmed rows.

Teachers can import only into their own active sections. Administrators can import into active sections. The server verifies the requesting user's access before creating or linking an account. Only student accounts can be created through this flow. The server stores the import marker and a digest of a randomly generated starter password to recognize safe retries. Passwords are managed by Supabase Auth.

1. Run `supabase/phase86_section_roster_import.sql` in Supabase SQL Editor.
2. With an authorized Supabase CLI session linked to the GradeRaid project, run `supabase functions deploy import-section-roster --no-verify-jwt`. The function verifies the bearer token itself with Supabase Auth and performs server-side authorization. Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to the hosted function.
3. Open the updated site and try a small roster in a test section. Verify sign-in, change a starter password, then sign in with the new password. The local tests exercise the spreadsheet UI and database logic against fixtures. Hosted Auth and quota availability need verification in the target project.

The workbook is parsed in the browser, and only student names and provisioning fields reach Supabase. A 30-student import makes roughly 30 Edge Function calls plus their Auth/profile writes, with extra calls for retries. There are no signup emails, Storage uploads, or recurring roster-import downloads. The daily cap of 200 new reservations per staff account is an application limit. Supabase applies its own Auth rates, Edge Function limits, and organization quotas. A whole class signing in over shared Wi-Fi can encounter rate limits depending on project settings. If the organization has restrictions in effect, the import still depends on working Supabase Auth and database APIs.

Free plan documentation lists 50,000 monthly active Auth users, 500,000 monthly Edge Function invocations, and 5 GB uncached egress across an organization. A small roster is unlikely to materially affect the egress budget, though sign-ins, lessons, raids and asset downloads count toward the appropriate service quotas.
